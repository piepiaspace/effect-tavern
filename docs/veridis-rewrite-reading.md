# 读表记录：Veridis Rewrite，酒馆生态里的「去八股」基底与局部润色思路

2026-11-27。研读对象：[The-Veridis-Lion/Veridis-Rewrite](https://github.com/The-Veridis-Lion/Veridis-Rewrite)（基于上游 `3.5` 的 `3.5.0-fix.37` 分支，前身为 `ultimate_purifier` → `ultimate_purifier_ai_rewrite`，DOM 前缀 `blai-`）。全仓 `src/` 共约 2.47 万行 JS、`templates/purifier.html` 934 行模板、`tests/` 下 26 个回归测试文件。

关联背景：项目中的 **Issue #244**（Polish 引擎与前端重构调研，最终收敛见文末补记与 **#267**）。对照源码可以直接确认：**我们早期的 `packages/runtime/src/polish.ts` 原型（`hit-1` 靶标命名、`*` 短跨度通配、`<target>` 内联包裹、`{ [id]: string }` JSON 映射）在形态上正与 Veridis 同源**，只是当时快速搭原型时既砍掉了它的「确定性程序替换层」与「规则级改写指令」，又把默认 Prompt 收紧到了极度保守的「禁删句、保原长」状态。

## 0. 先看思考主线：为什么酒馆资深玩家至今最认可「正则基底 + 局部改写」？

在拆代码之前，先回答最关键的问题：**为什么社区折腾了一圈之后，真正立住脚的还是这套看似朴素的「规则驱动改写」，而更大规模的「通篇 AI 重写/二稿润色」方案在酒馆生态里一直没跑出来？**

从 Veridis 从 `1.x`（纯正则净化器）到 `3.5` 的演化轨迹里，可以看到四条非常扎实的领域直觉：

### 0.1 八股文的二八定律：80% 是「表层口癖」，20% 才是「句法套路」

中文 RP 模型生成的「八股」并不是铁板一块，Veridis 在产品结构上把它切成了两类完全不同性质的问题（见 `src/rules/engine.js` 与 `src/aiRewrite/matching.js`）：

| 问题层级 | 典型表现 | 最优解法 | 为什么不能用另一种解法替代 |
| :--- | :--- | :--- | :--- |
| **表层词汇/标点癖（~80%）** | 高频赘余副词（`不由自主地`、`生理性地`、`微微`）、滥用破折号 `——`、固定口头禅前缀、可同义轮换的套话 | **Program Rewrite**（普通文本 / `{A,B}*` 简易通配 / 正则 `$1` 剥壳 / 留空直接删除 / 多候选随机替换） | 调 LLM 处理这类词纯属算力浪费：不仅慢、贵，而且容易为了改两个字把整句原本对味的语气改丢 |
| **结构性句式/陈词滥调（~20%）** | `不是A，而是B`、`像一颗石子落入湖心`、`指节因用力而泛白`、`带着一丝几乎可以称之为“X”的意味` | **AI Rewrite**（提取命中所在的句子，附带该规则专属改写要求，交由模型重组整句） | 纯正则删改会直接把句子拆成病句或残句，必须重新组织主谓宾与前后衔接 |

**为什么大规模全文 AI 润色在酒馆跑不出来？**

1. **二次八股化（Voice Flattening）**：主生成模型带着完整的角色卡声线、前文情绪张力写出了初稿；如果后置一个通篇改写调用，润色模型极易用一种「干净但平庸的编辑腔」把主模型原本灵动的短句节奏和人物口吻磨平，甚至把主模型的八股换成润色模型自己的八股。
2. **改动半径失控导致信任崩塌**：全文改写是黑盒，一旦悄悄改掉一处伏笔、否定词或微妙态度，玩家根本不知道该调哪个旋钮，被坑两次就会彻底关掉功能。而基于规则触发的局部改写是**指哪打哪、未命中处逐字不动**。

### 0.2 去八股的真正收益不只是「当轮好看」，而是「阻断 ICL 滚雪球」

正如我们在 [airp-craft-reading.md](./airp-craft-reading.md) 里总结的：**In-Context Learning 像重力**。只要第 1 轮回复里留下了两个 `——`、一句 `不是……而是……` 和一个 `指节发白`，它们进入下一轮历史上下文后，模型到第 15 轮就会整段复读同类句式。

资深玩家之所以把 Veridis 当作「基底工具」（甚至专门用它的 `Deep Clean` 去洗角色卡开场白和世界书），核心诉求其实是**转录稿卫生（Transcript Hygiene）**——在坏模式进入历史前缀之前把它掐灭。

### 0.3 `3.3` 版本的关键反转：为什么顺序必须是「先 AI 局部改写，再跑普通规则净化」？

这是一个极易被直觉想反、但经过实战验证的细节（见 `README.md` 与 `src/aiRewrite/apply.js`）：

```mermaid
flowchart LR
    A["主模型原始正文 (Original)"] --> B["1. AI 局部改写命中句 (AI Stage)"]
    B --> C["2. 普通规则全局扫尾 (Program Stage)"]
    C --> D["终稿落盘 + 三段式 Diff 记录"]
```

早期版本曾是「先跑普通规则，再喂给 AI」，在 `3.3` 被明确翻转为 **`Original → AI → Program`**，原因有二：

1. **给 AI 完整的原始语法上下文**：如果先跑正则删词，很容易造出残缺病句，AI 看到残句会误判原意；
2. **用确定性规则给 AI 自己「擦屁股」**：润色模型自己在重写句子时，照样可能顺手写出 `忽然`、`微微` 或破折号 `——`！把确定性规则放在最后一道关卡，能顺手把润色模型新带进来的表层口癖一并清干净。

### 0.4 规则不是「禁词表」，而是「探测器 + 处置方式 + 编辑微指令」

对比我们目前 `packages/runtime/src/polish.ts` 里单薄的 `{ pattern, hint?, max?, enabled? }`，Veridis 的单条子规则（见 `templates/purifier.html` 与 `src/aiRewrite/planning.js`）把职责拆得非常清楚：

- **所属合集（`Rule.name`）+ 单条备注（`remark`）**：面向**人类用户**的分类管理与可读说明（如合集「程度副词与认知失能净化」、备注「处理特定角色口头禅」），支持按合集整组开关、导出分享；
- **匹配模式（`mode` + `targets`）**：支持 `text`（纯字面合并成单一大正则极速匹配）、`simple`（`*` 跨度 ≤15 字且不跨标点，外加 `{A,B,C}` 候选分支语法）、`regex`（完整正则 + 空串匹配安全拦截）；
- **处置模式（`rewriteMode: "program" | "ai"`）**：决定走零成本代码替换还是走模型改写；
- **替换候选池（`replacements`）**：`program` 模式下为空即**直接删除**，单项即替换（支持 `$1` 捕获组），多项即每次命中独立随机抽取；`ai` 模式下则充当**流式生成期间的临时视觉遮罩 + AI 请求失败时的确定性回退**；
- **单条改写要求（`aiPromptTemplate`）**：面向**润色模型**的具体改写动作指导（如「命中 A 组时只弱化不删除；命中 B 组时删去比喻改写为具体动作；必要时允许返回空串删去整句」）。同一句命中多条规则时，去重编号为 `r1, r2` 注入 `<rewrite_target id="hit-1" rules="r1,r2">`。

## 1. 三重方法拆解 Veridis Rewrite

用项目一贯的三把尺子把 2.47 万行代码分堆，能立刻看清什么是宿主包袱、什么是死胡同、什么是真金白银。

### 1.1 第一重：为酒馆（SillyTavern）打的宿主补丁（约占 65% 代码量）

去掉 SillyTavern 的四大结构缺位（消息是脏字串、回合无阶段、连接无路由、历史无日志树），以下模块全部失去存在理由：

| ST 的底层缺位 | Veridis 被迫长出的补丁模块 | 代码落点 |
| :--- | :--- | :--- |
| **消息是混杂脏字符串** | CoT、状态栏、变量更新全糊在 `msg.mes` 里，被迫做 `xmlScopeTag: "content"` 正文提取、流式尾部闭合扫描、`scope/` 标签保护/内净模式、硬编码剥离 `<UpdateVariable>`、掩码 HTML 注释、绕开 MVU 状态栏占位符与保留 MVU 追加尾部 | `src/aiRewrite/matching.js`、`src/scope/`、`src/text/variableUpdates.js`、`src/integrations/mvu.js` |
| **回合没有一等阶段** | 只能在宿主 DOM/生成事件缝隙里抢时机，维护 1,300 行的异步任务编排、新鲜度校验、防重入锁；流式期间不能改源文本，被迫造一套操作 `.mes_text` DOM 的逐帧视觉投影与随机候选帧间记忆；还要跟 Shujuku 填表插件做跨插件回调同步（近 3,500 行） | `src/aiRewrite/runtime.js`、`src/host/generationLifecycle.js`、`src/dom/streaming.js`、`src/shujuku/` |
| **没有阶段级模型连接** | 自己维护一套完整的 Base URL / API Key / 采样参数 / API 预设管理；平时借道 `TavernHelper.generateRaw` 发请求，遇到 Luker 规则路由或 TauriTavern 误判主生成时又切回 ST `/api/backends/chat-completions/generate` 代理，并手写 YAML exclude 清洗主预设参数污染 | `src/aiRewrite/generation.js`、`src/aiRewrite/isolatedRequest.js`、`src/aiRewrite/requestOptions.js` |
| **扁平 `chat[]` 与 `swipes[]`** | 没有不可变树，只能在 `msg.__blai_diff_branch_meta["swipe:N"]` 里塞三份全文快照，宿主删 Swipe `splice` 数组后手动平移键名，并设置滑窗上限（默认只留最近 3 楼对比文本）防止撑爆 `chat.jsonl` | `src/diff/messageMeta.js`、`src/diff/retention.js` |
| **预设缺少分层叠放** | 自建「角色绑定 > 对话补全预设绑定 > 全局默认」三级互斥解析器，外加大量历史字段破坏性迁移代码 | `src/presets/bindings.js`、`src/settings/migration.js` |

### 1.2 第二重：自成一派的野路子（核心反面教材与方向错配）

这一部分是本次研读**含金量最高**的发现——它直接揭示了当局部改写试图放开手脚时，为什么会在错误的技术边界上撞墙：

#### 1. 「半句坐标拼接 × 鼓励自然重组」引发的 700 行中文语法特判泥潭

> [!WARNING]
> **局部改写头号工程陷阱**：一旦把编辑靶标切得比「自然语法孤岛（完整句/自然段）」更碎，同时又在 Prompt 里允许模型「重组语序、删减整句」，模型输出与字符坐标拼接之间就会爆发不可调和的边界冲突。

看看 Veridis 是怎么一步步掉进这个坑里的：

1. **切碎边界**：`src/aiRewrite/matching.js` 把成对引号（`“”`、`「」`）、括号、`*...*` 当作外部包裹边界切开，导致频繁产生**半句靶标**。例如原文：
   `管理员的语气里甚至带上了一丝可以称之为“亲切”的笑意，“请进。”`
   命中 `称之为` 规则后，切出来的 `<rewrite_target>` 只有前半截：`管理员的语气里甚至带上了一丝可以称之为`，而后半截 `“亲切”的笑意，“请进。”` 被锁进 `<locked_context>`。
2. **放开指令**：从 `tongYong14` 到 `Protocol 8`（`src/settings/defaults.js`），Prompt 明确鼓励模型：「不要只机械删除或替换命中词……重新组织整个目标文本；允许删除整个目标返回空字符串」。
3. **模型必然越界补全**：LLM 是按语义成句思考的，绝不会老老实实停在半截悬空动词上。于是模型高频出现四类事故：
   - 把紧邻 `<locked_context>` 里的 `“亲切”的笑意` 顺手抄进返回值 → 原位拼接后变成双份复读；
   - 把下一句的因果或转折分句合并进当前句（如把下一句 `那是归档，是备份` 合进当前句变成 `……而是归档，是备份`） → 下文整句重复；
   - 把 `那一声迟疑的“好！”，像一颗石子落入心中。` 的后半句直接删空返回 `""` → 只剩悬空主语 `那一声迟疑的“好！”`；
   - 遇到复杂边界干脆原样返回不改。
4. **用几百行特判正则打地鼠**：从 `fix.16` 到 `fix.37`（见 `CHANGELOG.md`），分支作者被迫写出了 `boundaryDialogue.js`（275 行）、`boundaryCompletion.js`（79 行）、`adjacentContinuation.js`（107 行）、`narrationCopies.js`（119 行）——里面甚至有专门匹配 `/^([他她它])不是在([\p{L}]{2,6})[，,]而是在([\p{L}]{2,6})。$/u` 这种单一句式的硬编码外科手术！在 `fix.34` 还尝试过让模型输出 `{ before, occurrence, after }` 局部锚点数组（`localEdits.js`），结果因预设兼容与遵从度问题在 `fix.35` 立刻回退。

#### 2. 无头裸调（Context-Blind Rewrite）：润色模型看不见角色卡与叙事设定

看 `src/aiRewrite/generation.js`：Veridis 发给模型的永远只有一条孤零零的 `{ role: "user", content: prompt }`，里面只有全局指令、触发规则和最多 `12000` 字的当前消息切片。**润色模型完全不知道角色是谁、世界观是什么时代、第二人称还是第三人称**，只能靠 `<source>` 里没被命中的句子盲猜文风。一旦某段密集命中，改出来的句子极易脱离角色声线。

#### 3. 事后倒推「可能相关规则」（Heuristic Attribution）

因为 `engine.js` 把所有字面规则压成一个大正则直接替换，没留执行轨迹，用户在「前文透视」里点击某处差异想看是哪条规则干的时，`src/diff/relatedRules.js` 只能遍历当前规则库做 8 档启发式打分（`exactDeleted: 80`、`context: 20`）去「猜」凶手。

#### 4. 浏览器扩展里的重型全家桶

内置从 GitHub 动态拉取并校验 OpenCC 简繁词典包（`zh/`）、带 5×10MB 文件上传的匿名工单客户端（`feedback/`）、以及横跨聊天/角色卡/人设/世界书/Shujuku 数据库的批处理重洗工作台（`deepClean/`）。

### 1.3 第三重：我们的 Harness 已经具备更先进实现的维度

| 维度 | Veridis Rewrite 的做法 | Effect Tavern 现有 Harness 的形态 |
| :--- | :--- | :--- |
| **执行时机与记忆卫生** | 聊天落盘后异步抢改，还要专门写几千行去洗 Shujuku 数据库和旧楼层 | `narrate → check → polish → record` 原生串行阶段（`packages/runtime/src/session.ts`）：**先润色完，再进 `record` 提取世界状态与事件摘要，最后落不可变节点**，天然零脏数据入库 |
| **作品与角色语境在场** | 裸发单条 `user` 消息，靠残余上下文盲猜人设与视角 | `polish` 原生穿戴 `reviewed`（含 `<world>` 故事设定 + Hat `review.head`，见 `packages/runtime/src/request.ts`），天然共享前缀缓存与世界观基调 |
| **对白保护与切句完整性** | 引号切在编辑范围外，制造大量「半句靶标」引发回抄灾难 | `packages/runtime/src/polish.ts` 用 `mask()` 在扫描时屏蔽对白与心声引号（`「」『』“”‘’`）内的口语，但**切句时把含引语的整句完整交出**（如 `他说：「好。」` 不拆碎），从根源上杜绝引号切半句 |
| **高频词密度阈值** | 无频次概念，命中一次即杀（导致不敢把 `像`、`仿佛`、`的` 写进规则） | `Entry.max` 千字频次上限（`polish.ts`）：允许适度使用比喻词，仅当千字密度超标时才标记清理——这是比 Veridis 更懂文学审美的机制 |
| **配置分层与随卡分发** | 全局 / 补全预设 / 角色三级互斥绑定 | `Card < Pack < Player` 确定性叠放栈（`packages/runtime/src/layer.ts`），支持 `enabled: false` 精确关停下层规则，且复用于工坊 `lint.ts` 卡片静态体检 |
| **结构化输出与分支历史** | 手写 Prompt 警告 + `JSON.parse` + 消息内挂三份全文备份 | 原生 `Schema.Struct` 结构化返回 + `Log` 不可变节点树（重润色天然就是 sibling 分支，Inspector 原生留存请求与前后对照 `polishPairs`） |

## 2. 第一阶段推演记录（读完 Veridis 时的初步假设）

读完 Veridis 时，曾一度设想按「L0 确定性净化 + L1 自然段靶向重塑 + L2 全篇二稿精修（Editorial Brief）」三级光谱来展开 Issue #244。其中有两点关键工程判断在后续讨论中被保留了下来：

1. **绝不能做「半句坐标切分」**：只要允许模型调整语序或删减注水废话，靶标边界就必须是闭合的自然句或相邻命中句群/自然段，否则必掉进 700 行中文标点与引号接缝补丁的泥潭。
2. **修复无头盲改**：我们当前的 `polish` 虽然穿戴了 `<world>`，但 `worldOf` 剥掉了所有 `WRITING` 槽位与写作包片段，导致 `polish` 依然看不见当前写作包的人称、语言与文风要求，必须补齐。

## 3. 补记：结合跨生态调研后的最终定调（#267 / #268）

在进一步对照了 [现代 Agent Harness 与长篇网文工业化润色流水线](./modern-polish-survey.md) 并回到 Tavern RP 的本质场景推敲后，我们推翻了「把 Polish 做成重型多模式独立润色工作流（L0/L1/L2 + Editorial Brief）」的扩张方向，最终收敛为两条明确结论：

1. **Polish 收敛为极简的「正则/通配快筛 + 有限语义微调」（见 Issue #267）**：
   - Tavern RP 不是追求 80 分发表成品的网文工业流，它讲求即时情感反馈与下一轮的推进钩子，无法承受与正文同量级的二稿重写耗时；Polish 只需在极低延迟下将 50 分套路腔拉回 60 分顺畅线（无命中 0 调用，命中单次轻量改写）。
   - 「错误的套路写法有限，正确的写法无限。」Polish 只做**纯粹的负向压制**，不内置 `Before → After` 范例或复杂润色方针；重点修好现有简化架构里的死板束缚（放宽句长与冗余删减限制、守住完整句/句群边界）、向 `polish` 透传生效的 `<writing_guidelines>`，并理顺 `LexiconEntry` 的字段语义与 `max` / `enabled` 暴露。
2. **正向文风归回写作包，并解除写作包双原语的硬编码包办（见 Issue #268）**：
